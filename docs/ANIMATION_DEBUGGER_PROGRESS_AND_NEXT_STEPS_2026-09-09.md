## 5. 当前数据语义与限制

- **状态名称**：目前使用状态哈希作为可靠标识，不反解或猜测状态名称。
- **Clip 时间**：从 ClipPlayable 直接读取；仅有 Animator ClipInfo 时，时间和速度保持未知，不用状态长度推算。
- **权重**：显示局部输入权重或 Animator 报告权重，不将不同来源相加，也不宣称是最终骨骼贡献。
- **角色名称**：目前主要来自 Transform / Animator 对象名称，不保证是角色本地化姓名。
- **跟随模式**：当前角色下只有一个 Animator 时自动选中；多个候选时提示手动选择。
- **实例身份**：固定选择保留对象引用，失效后不会因 ID 复用而自动换对象；Animator ClipInfo 的数组序号本身不是稳定播放实例 ID。
- **图结构**：当前逐样本保存完整节点信息，并根据变化产生事件；尚未通过共享拓扑版本压缩重复结构。
- **记录保存**：会话首先在内存中保存，导出后才形成正式文件；强制结束进程不能保证保留未导出的部分。
- **容量**：限制是保守估算的记录容量，不是整个进程内存上限；复杂图可能在时长上限之前达到容量上限。
- **窗口**：为独立线程上的桌面置顶窗口；独占全屏和不同 DPI 下的表现尚未确认。
- **历史查看**：窗口事件列表最多显示最近 500 条，完整事件保留在导出中；暂不支持从磁盘重新载入旧会话。

这些限制需要在使用说明和能力矩阵中明确，不通过补零、虚构状态名称或推算最终权重掩盖。

## 7. 后续开发计划

### 第一优先级：同步使用说明与需求覆盖情况

1. 静态梳理第二轮改动与 V2 需求的对应关系，确认配置、窗口和导出字段采用一致命名与单位。

3. 补充新配置项、`metadata.json`、实际采样统计和方法级异常的使用说明。
4. 后续改动继续按明确范围做本地 Git 提交；两份原计划文档和 `artifacts` 中的工作产物不自动纳入提交。

### 第二优先级：完善交付说明与剩余代码边界

1. 建立按字段、来源、失败表现划分的能力矩阵，区分“代码已接入”“本地模拟检查过”“实际客户端待确认”。
2. 继续静态检查目标切换、配置刷新、停止记录和异常隔离之间的状态边界，有确定问题时修正代码。
3. 明确采样统计的分母、缺失样本处理方式和采集耗时范围，避免被误读为游戏性能结论。
4. 整理发布文件与启用流程，确保用户可以从主控制器配置功能，并找到记录输出。

### 第三优先级：按需要优化，不扩大需求

- 若记录体积成为实际使用问题，再引入图拓扑版本共享或其他有界存储优化。
- 若拿到可靠的角色名称或稳定播放实例来源，再改进目标标签与实例识别，不靠名称猜测关系。
- 磁盘历史重载、图形化时间轴等作为增强项，不应挤占核心实时调试与记录需求。

### 保留待确认，不由助手执行

真实游戏中的待机、移动、攻击、技能、多 Clip 混合、角色/场景切换，以及持续运行与性能指标，仍需由用户后续确认。
